# TR-06 — Мульти-транспортный канал с failover

| | |
|---|---|
| Область | ядро + оркестрация |
| Приоритет | P1 |
| Статус | open, заблокировано наличием живых посредников |
| Зависимости | TR-01/TR-03/TR-04/TR-05 (хотя бы один живой лейн), CORE-03 |
| Апстрим | Desktop-клиент заявляет «multi-transport sessions with automatic failover» из коробки |

## Проблема

Сегодня канал = один лейн (direct). Исторически сессия апстрима
умеет несколько лейнов с автопереключением — это заявлено в
Desktop-клиенте. Для продуктового VPN это главный резерв
устойчивости: direct умер (заблокировали IP) → канал сам переезжает
на посредника и обратно. Наша оркестрация (ссылки, конфиги каналов,
выпуск через бот) про мульти-лейн ничего не знает: ни конфиг ноды,
ни `openflux://`-ссылка, ни docprovider-часть выпуска не готовы.

## Ожидаемый результат

- [ ] конфиг канала описывает упорядоченный список лейнов с
      приоритетами; ссылка несёт то же множество (расширение формата —
      через апстрим, кодек не переизобретать: CLI-09);
- [ ] failover подтверждён живым тестом: убит primary-лейн → туннель
      восстанавливается на запасном за ≤ N секунд без действий
      пользователя, возврат на primary — по стабилизации;
- [ ] выпуск в бот/oflux-admin создаёт мульти-лейн канал одной
      командой; для юзера ничего не меняется (одна ссылка, один QR);
- [ ] видно, на каком лейне канал едет сейчас (в `/status` и в
      метриках SRV-03);
- [ ] лейны с куками (TR-01) участвуют в failover без ручного
      пересеивания.
