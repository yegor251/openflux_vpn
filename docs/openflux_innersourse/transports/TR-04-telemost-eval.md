## Проблема

В ядре появился транспорт, где туннель едет видеоконференцией Яндекс
Telemost: SFU релеит RTP-стримы, ядро кладёт поверх свой in-order
ARQ. Апстрим меряет 4.4–5 MB/s стабильно. Это **маскировка под
видеозвонок** — ровно та ниша, которую у нас освободили яндекс-доки
(TR-01), но без куков и капчи: конференция живёт по ссылке.
Ограничения апстрима: одна конференция = один клиент+exit; desktop
full-tunnel пока отказывается (риск media-loop), мобильные клиенты
через VPN-интерфейс — ок.

## Оценка 2026-10-23 (ход, живые проверки)

Факты из исходников и лайв-проб (curl к `cloud-api.yandex.ru`):

| Проверка | Результат |
|---|---|
| Вход в конференцию (JOIN) | **гостевой, без кук**: запрос connection по несуществующей ссылке → `404 ConferenceNotFound` (не 401) — дата-плейн не зависит от свежести кук и не проходит капчи посреди сессии |
| Создание конференции API-ем | **требует авторизации**: без кук 401; с нашей боевой док-сессией тоже 401 («Не авторизован») с VPS и с домашнего IP — cloud-api-аутентификация ≠ док-сессия; авто-создание ядром (пустой URL → POST с Cookie+X-Uid) у нас не работает |
| Конфиг ноды | `node.conf` — INI `[Transport telemost] Type/URL` — секция пишется руками; **инсталлятор telemost-ключа не имеет** (productization = добавить `TELEMOST=` в make_fork при положительном вердикте) |
| Desktop full-tunnel | ядро само отказывается (media-loop guard, `hasTelemost`) — клиенты: socks5-режим или Android VPN |
| iOS | известный убийца: NE гибнет через 4 c (#190) — iOS-юзеров на telemost не сажать до апстрим-фикса |

Смена модели эксплуатации против док-переносчиков: конференция
создаётся **один раз админом в браузере** (30 c под своим аккаунтом),
ссылка зашивается в канал; JOIN обеих сторон без кук. Капча-риск
остаётся только в момент создания руками — то есть на человека, а не
на headless-ноду. Не выяснено (для PoC): время жизни мгновенной
конференции-ссылки, поведение при смерти конференции (честная смерть
туннеля), goodput с нашего VDS, суточный soak.
