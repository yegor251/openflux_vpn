# TR-11 — Релей капчи: клиент проходит проверку за exit

| | |
|---|---|
| Область | транспорты-посредники |
| Приоритет | P2 (актуально при возврате капчных носителей — yandex/boards) |
| Статус | проверено 2026-10-25: детект+запрос работают на нашем стеке;
завершающий шаг (человек в браузере) существует только в приложениях.
Прямых носителей в проде нет — механизм сейчас не задействован. |
| Апстрим | `TestMatrixAuthRelay` (ядро) — механизм покрыт тестами |
| Источник | живой стенд canary-2 (yandex-лейн за SmartCaptcha) + исходники ядра 12c278e |

## Как устроено в ядре

1. **Детект (exit):** носитель упирается в капчу (`errCaptchaRequired`) →
   `ErrorNotifier` → `Manager.NotifyCaptcha` → `SubtypeAuthRequired`
   летит клиенту по живому носителю (rate-limit на повтор).
2. **Запрос (клиент):** `remoteAuth`-нотификатор; CLI поднимает локальный
   auth-прокси и отдаёт ссылку в IPC-статус-сервер — браузер показывает
   её **приложение** (десктоп/мобильное), CLI сам ничего не решает.
3. **Решение (человек):** проходит проверку в браузере приложения.
4. **Возврат:** приложение кладёт jar через IPC (`SendCookiesOffer`) →
   `Manager.OfferCookies(reason="solved")` → exit `AcceptCookies` →
   лейн оживает, jar сохраняется в CookieStore ноды.
5. **Обратно (exit→клиент)** куки утекают только «shareable» — без
   логин-кук (`shareableCookies`); клиент сам периодически просит
   рефреш (`managerRefreshLoop`).

## Проверено живым стендом (2026-10-25)

- canary-2 (yandex P100 + direct P50, SmartCaptcha на VDS-IP): клиент
  аутентифицируется, через **10 c** получает
  `[MANAGER] the exit's carrier "yandex" needs a check in a browser
  (smartcaptcha): <doc-url>` — детект и доставка запроса работают.
- Засев CookieStore КЛИЕНТА свежими куками (`make_client_cookiestore.py`)
  **не** лечит exit: сеянные куки кормят только собственный лейн клиента,
  автоматического пуша на exit нет — по дизайну. Кук на клиенте сегодня
  тоже не хватило (закрытие 1005 — док канарки от 20.10, отдельный вопрос).

## Что это значит для нас

- В проде (direct-only) капча невозможна в принципе — релей не задействован.
- При возврате капчного носителя: завершающий шаг делает **приложение**
  (браузер внутри + IPC к ядру). CLI-клиентам — только сеять CookieStore
  вручную (лечит их лейн, не ноду) или refresh_cookies.py на ноду.
- Десктоп 3.12.2 в нашем прогоне писал «Нет связи с ядром по IPC» — пока
  IPC не жив, браузерный шаг капчи в приложении не сработает; проверить
  в CL-05 (это же чинит «второй раз с sudo»).
