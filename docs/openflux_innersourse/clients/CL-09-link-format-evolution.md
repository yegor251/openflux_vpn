# CL-09 — Эволюция формата `openflux://`-ссылки

| | |
|---|---|
| Область | ядро + оркестрация |
| Приоритет | P2 |
| Статус | open |
| Зависимости | TR-06 (мульти-лейн), CORE-08 (версии), SEC-03 (ротация) |
| Апстрим | кодек ссылок в ядре (--make-link/--parse-link); мы сознательно не переизобретаем (subprocess only) |
| Источник | **продуктовая логика** (что продукту нужно от ссылки) + **наше правило** из CLAUDE.md (кодек — только subprocess бинаря); требований в апстриме нет — их и надо сформулировать |

## Проблема

Ссылка сегодня несёт: ключ, URL доков-носителей, direct_dial. Для
продукта не хватает: множества лейнов с приоритетами (TR-06), подсказки
минимальной версии клиента (CORE-08), признака «ссылка устарела»
(ротация ключа у юзера — старый QR должен говорить «ротирован,
возьми новый», а не молча не коннектиться). Формат — вотчина апстрима;
форкать кодек мы себе запретили (CLAUDE.md).

## Ожидаемый результат

- [ ] список требований к следующей версии формата, согласованных с
      реальностью апстрима (что уже можно, что надо просить);
- [ ] для каждого требования — статус: есть в ядре / issue подано /
      ждём; ничего не реализуется в обход кодека ядра;
- [ ] graceful-деградация: старый клиент на новой ссылке даёт
      понятную ошибку, а не мусор (проверено);
- [ ] QR-практика: подтверждено, что длинные ссылки сканируются
      основными камерами юзеров (замер на 2–3 устройствах), иначе —
      план Б (текстовый импорт).
