# План работ: multi-user VPN на OpenFlux (прод: direct; запасные проверены)

Цель: готовое решение «личный VPN для многих пользователей» без
бизнес-части. Каждый пользователь — свой канал: ключ + exit-инстанс на
VDS + openflux://-ссылка. Управление — CLI на машине администратора,
пользователи — Telegram-бот.

```
oflux-admin (наш код, Python)
   │ ключ + SSH node-install.sh + openflux://-ссылка
   ▼
VDS: systemd-каналы openflux-node@<user> (по одному активному клиенту)
   ▲
пользователь: openflux://-ссылка → готовое приложение (Desktop/Android/iOS)
```

Бэклоги: `docs/openflux_innersourse/` — апстрим (ядро, клиенты,
транспорты; 3 файла), `docs/openflux_service/` — наш сервис (бот, VPS,
эксплуатация; 5 файлов). Технические подробности библиотеки —
`src/docprovider/README.md` и исходники ядра.

## Транспорты: прод и запасные (вердикты 2026-10-24)

Замеры и механика — `docs/openflux_innersourse/transports/TR-10-new-transports-research-base.md`.
Критерий запасного: анонимность → стабильность → скорость.

| транспорт | статус | goodput | роль |
|---|---|---|---|
| **direct** | прод | 2.5–3.7 MB/s | основной канал всех пользователей |
| **telemost** | работает | ~854 KB/s (30 МиБ) | запас №1; маскировка под видеоконференцию; блокер handshake закрыт ядром 0.15.x (TR-08 закрыт — отчёт в апстрим не нужен) |
| **cupsonline** | работает | 0.29–0.44 MB/s | запас №2; браузер/мессенджеры, не для загрузок |
| avito | мёртв с VDS | — | анти-абьюз датацентровых IP (ERR_ROOM_NOT_FOUND, join-шторм); пере-тест только с куками браузера (`--avito-cookies`) |
| yandex / mailru / vyandex | мертвы | — | #106/#193, sign-in; не возвращать без внешнего события |
| pruffme / mtslink / bitrix | не проверены | — | JS-пакеты; нужен клиент с вкладкой Transports; отложено до надобности |

**Когда переключать канал на запасной:** только если direct пропал
(блокировка хостингом/провайдером/РКН-класс; контекст маскировки —
`docs/WHY_MASKING.md`). Скорость запасных в 3–10 раз ниже — это
аварийный путь, не апгрейд.

**Как переключать (сегодня, руками):** exit-нода — секция
`[Transport telemost]` (или cupsonline) в node.conf; для cupsonline
exit без URL создаёт комнаты и печатает base64-список «COPY THIS TO
CLIENT» — он идёт в `URL` клиентской секции; telemost-ссылке нужна
живая конференция (создание — под Yandex-логиной админа, join
гостевой; с VPS создать нельзя — cloud-api 401). Клиент — та же
секция + тот же ключ. Приложениям (3.10.x) транспорт ставится
вкладкой Transports из каталога подписанных пакетов.

**Мульти-транспорт и фейловер.** Формат ссылки умеет мульти-транспорт
(`transports[]` с приоритетами — старые каналы так работали), но
**авто-фейловер на ядре 0.15.x не работает**: PoC 2026-10-25 (direct +
cupsonline в одной сессии, тихая смерть direct) показал деградацию —
сессия циклит KDF-кандидаты, stripe-состояние перезапускается, 3–10
KB/s вместо 185 (детали и repro — TR-10). В прод не включать до фикса
ядра; кандидат в апстрим-issue. Переключение на запасной — ручное,
по плану выше.

**Незакрытые проверки запасных:** idle-поведение (cups 35+ мин,
telemost 15+ мин — ставились 2026-10-24), смерть носителя = честная
смерть туннеля, прожитые сутки на фоне. До них запасные считаются
«проверены на подъём и скорость», не более.

## Живое (открытые пункты)

- **CL-01** Android 3.10.3 приёмка (главный шаг; затем PRD-02
  `/download`, затем PRD-05 онбординг e2e и хвост OPS-01 — второй

  пользователей.
- Ограничение revoke: яндекс-док остаётся опубликованным (метода
  отзыва нет) — актуально только при возврате посредников.
- Нагрузочная проверка 10–20 каналов на VDS (1 GB) и критерий «неделя
  5+ каналов без ручного вмешательства» — перед ростом.

## Открытые вопросы

- Верхняя граница каналов на один VDS до деградации (l3 ест память на
  соединение) — измерить в нагрузочной проверке.
- DNS клиента через tun (UDP NAT в l3) — проверять живым tun-клиентом;
  socks5-стенды этот путь не трогают.
