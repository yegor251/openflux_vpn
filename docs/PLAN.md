# План работ: multi-user VPN на OpenFlux (канал: direct; посредники отключены)

Цель: готовое решение «личный VPN для многих пользователей» без
бизнес-части. Каждый пользователь — свой канал: ключ + exit-инстанс на
VDS + openflux://-ссылка. Управление — CLI на машине администратора.

```
oflux-admin (наш код, Python)
   │ ключ + docprovider + SSH node-install.sh + openflux://-ссылка
   ▼
VDS: systemd-каналы openflux-node@<user> (по одному активному клиенту)
   ▲
пользователь: openflux://-ссылка → готовое приложение (Desktop/Android/CLI)
```

Технические подробности библиотеки и модуля документов — не здесь:
`src/docprovider/README.md` (поведение docprovider, live-контракты API,
грабли) и исходники `OpenFlux/`.

## Состояние (2026-10-18)

Канал `of-alice` работает end-to-end (клиент на MacBook, трафик идёт).
**Режим канала — direct-only, l3**: шифрованное AES-256-GCM через
raw-SNAT, без двойной терминации TCP; goodput до 4.8 MB/s против
0.6–1.6 MB/s на l4 в те же часы. Без маскировки под белые сервисы —
оба транспорта-посредника отключены не нами, а внешними событиями:

- **mailru** — Mail.ru закрыл анонимный доступ к публичным ссылкам
  (апстрим issue **#193**, глобально, фикса нет). Модуль `docprovider/mailru`
  сохранён; транспорт возвращается одной веткой, если Mail.ru откатит
  политику (следить за #193).
- **yandex** — Яндекс перевёл оба наших IP (домашний и VPS) на
  SmartCaptcha/login-стены; у headless exit-ноды пути прохождения капчи
  нет по дизайну (апстрим issue **#106**, открыт). Cookie-store клиента
  сеется скриптом `scripts/make_client_cookiestore.py` (работает: клиентский
  лейн оживал), но exit-сторона сеяные куки не подхватывает + при каждом
  флапе мёртвого лейна сессия уходит в live-lock ренегоциации
  (context-chase; тоже кандидат в апстрим-issues). Итог: лейн убран из
  канала до изменения ситуации в апстриме. Doc, куки и все обвязки
  сохранены.

Замеры goodput (10 MB через полный туннель, mirror.yandex.ru):
direct+l4 = 0.6–4.3 MB/s в зависимости от времени суток.

## Сделано

- **M1 `docprovider`** — готов, live-верифицирован (2026-10-15).
- **M2 `oflux-admin`** — add-user/list/link/revoke работают; инсталлятор
  — наш форк (`deploy/make_fork.py`) с ключами `yandex=` и `mode=`.
- **Конвейер обновлений** — `scripts/update_openflux.sh` + авто-апдейт
  ядра ноды на сервере (таймер 6 ч, SHA-256 pin, rollback).
- **Live-тесты** — удалены после приёмки 2026-10-18 (восстановление:
  git-история, `tests/live/`).
- **l3-режим в форке** — ключ `mode=`, per-channel drop-in
  `AmbientCapabilities=CAP_NET_RAW`, iptables-правило против kernel-RST
  + oneshot-юнит на перезагрузку. Работает, канал переведён на l3.
  Две грабли, найденные при вводе (см. «Известные гонки апстрима»):
  RST-правило должно вставаться **первой строкой** OUTPUT (ufw-цепочки
  ACCEPT-ят `ctstate NEW` раньше appended-правил), а первое подключение
  к свежезапущенной ноде может попасть в зомби-сессию — лечится
  warm-up'ом в `Provisioner.apply`.

## Известные гонки апстрима (наблюдения 2026-10-18)

- **Зомби на первом подключении.** После старта юнита ноды первое
  клиентское подключение иногда аутентифицируется, но дата-плейн не
  возит пакеты (клиент циклит `[CRYPTO] no answer ...`, нода ACK-ит
  TCP-байты и молчит). Второе подключение к той же ноде всегда живое.
  На l3 и l4 одинаково — гонка биндинга лейнов в ядре сессии, не наш
  форк. Митигация: `Provisioner.warmup()` после apply (loopback-сессия
  на сервере съедает гонку). Не покрыто: рестарты каналов от
  авто-апдейтера (раз в 6 ч) — если пользователь подключится сразу
  после, может попасть в гонку; повторное подключение лечит.
- **Рестарт ноды под живым клиентом** — клиент-свидетель уходит в
  зомби и сам не восстанавливается (renegotiation live-lock, цикл
  `[CRYPTO]` контекстов). Лечится рестартом клиента. Операционное
  правило: любые манипуляции с нодой → пользователю переподключиться.
- Оба наблюдателя стоит оформить issue в апстрим с логами из
  git-истории этого репо.

## M5 — Telegram-бот (один для админа и пользователей)

**Один бот `oflux-bot`, живёт на хостинге** (VPS; `api.telegram.org`
доступен с него — проверено 2026-10-18, 302 за 0.2 c). Бизнес-логика —
только функции oflux-admin (дублировать выпуск/ротацию в боте
запрещено). На VPS бот работает с нодой ЛОКАЛЬНО (node-install.sh,
systemctl — без SSH к самому себе); SSH остаётся для чужих VPS.

### Роли

- **user** — обычный сценарий, сам себя обслуживает: попадает по
  одноразовому коду-приглашению (админ даёт deep-link
  `t.me/<bot>?start=<token>`, токен одноразовый, хранится в реестре),
  сам выпускает себе канал, сам перевыпускает ссылку. Видит только
  свой канал. Лимит: 1 канал на TG-ID (конфигурируемо).
- **admin** — whitelist TG-ID в конфиге: то же самое + `/list` (все
  каналы) и `/revoke <name>` любого канала (аварийные случаи).
  Отдельного «админского» параллельного CLI в боте НЕТ: команды
  админа в CLI остаются для особых случаев.
- Отвязка пользователя: админ перевыпускает токен (старый умирает),
  либо пользователь сам `/revoke`.

### Команды

- [ ] `/start`, `/start <token>` — приветствие + привязка по
      одноразовому коду; `/help`; неавторизованным — только `/help`
      и `/download`.
- [ ] `/download` — как поставить приложение (заглушки, оформить
      красиво): macOS CLI (`sudo ./bin/openflux --config=...`), iOS
      TestFlight (ссылка-заглушка; помнить: iOS-сборки могут не уметь
      negotiate), Desktop/Android (релизы апстрима, заглушка).
- [ ] `/issue` — выпуск своего канала: прогресс шагами («создаю
      док…», «поднимаю канал…»), в конце ссылка + QR-фото (~30 c).
      Лимит каналов на TG-ID; имя канала бот генерирует сам.
- [ ] `/my` — своя ссылка + QR-фото заново (частый кейс «телефон
      потерял»; ключ не меняется).
- [ ] `/rotate` — новый ключ для СВОЕГО канала (inline-подтверждение:
      старая ссылка умирает), потом новая ссылка + QR.
- [ ] `/revoke` — снятие СВОЕГО канала (inline-подтверждение, отчёт
      об уборке; см. ограничение yandex-unpublish).
- [ ] `/status` — doctor своего канала (unit/mode/port/док).
- [ ] **admin**: `/list` — все каналы; `/revoke <name>` — любого
      канала (аварийно). Больше админу в боте ничего не нужно.

### Алерты (в личку админу; watchdog-поток внутри бота)

- [ ] Куки: живая проверка упала → алерт «куки протухли, нужен
      экспорт» + напоминание раз в N часов, пока не обновят.
- [ ] Каналы/ноды: local-проба порта и `systemctl is-active` (бот на
      месте, SSH не нужен); недоступен K проб подряд → алерт,
      восстановился M проб подряд → «ok» (антидребезг K=3, M=2).
- [ ] **Массовый сбой**: ≥50% каналов разом → ОДИН агрегированный
      алерт, без спама по каждому; дедуп/кулдаун на тип алерта.
- [ ] Смерть самого VPS НЕ алертится (осознанно, решено 2026-10-18):
      бот на том же хосте; индикатор для пользователей — бот молчит.

### Размещение, секреты, источник истины

      `oflux-bot`, автозапуск, ротация логов. Исходящий HTTPS до
      api.telegram.org — единственная внешняя зависимость.
- [ ] Реестр `users.json` (ключи каналов!) и `ya-cookies.txt` —

- [ ] Компрометация VPS = все ключи каналов + яндекс-куки в одном
