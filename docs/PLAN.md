# План: личный VPN для многих, работающий сам

Цель: бот работает самостоятельно — генерирует и выдаёт ссылки сам.
Админ делает ровно одну вещь руками: **обновляет куки, когда приходит
алерт**. Всё остальное — выпуск, переезд между носителями, алерты,
бэкапы — автоматом.

```
oflux-admin / oflux-bot (наш код)
   │ выпуск каналов на носителях, ссылки openflux://
   ▼
VDS: systemd-каналы openflux-node@<user> (носитель = трафик)
   ▲
пользователь: ссылка → приложение (только носитель, адрес VDS не виден)
```

Бэклоги: `docs/openflux_innersourse/` (апстрим: TR-10/TR-11 — замеры и
механика носителей), `docs/openflux_service/` (бот/VPS). Секреты и
рутина — `CLAUDE.md`.

## Состояние (2026-10-26)

Работает и принято живыми тестами:

- **Выпуск каналов полностью автоматом на VPS**, носитель — один из двух:
  - **cupsonline** (0.15–0.4 MB/s): сет из пула; пул пуст → бот сам
    минтит 8 комнат на VPS; cups отказал (403-лимит) → фолбэк;
  - **telemost** (~0.85 MB/s): бот сам создаёт конференцию
    (`telemostconf.py`, сессия админа на VPS). Живёт ~24 ч без
    активности, продлевается использованием.
- **Ссылка = один носитель** (без адреса VDS; dual-ссылки не выдаём —
  деградация переключения в ядре 0.15.x, наш repro = апстрим #198).
- **Бот-самообслуживание**: `/issue` `/my` `/rotate` `/revoke`
  `/status` `/download` (кнопки), меню `/start`, открытая выдача без
  авторизации, чистка клавиатуры, фикс двойных нажатий.
- **Алерты** (watchdog, не шумят: K=3/M=2, кулдауны): 🔴/🟢 канал,
  🚨 один агрегированный массовый сбой, 🟠 куки, freshness бэкапа.
- **Смерть носителя → предупреждения, переезд руками** (2026-10-28):
  пробники страниц носителей → вердикт «носитель умер» (K=3, M=2) →
  каждому пользователю носителя одно предупреждение («сделай /rotate»),
  админу 🚨; бот сам ссылки не минтит. `/rotate`//`/issue` на мёртвом
  носителе переезжают на запасной; кулдаун смены канала 10 мин; флап
  носителя (3 срыва/час) глушится до стабилизации. Состояние —
  `carrier-state.json` (0600, вне git). Урок 2026-10-27/28: ночной
  авто-минт при сбойном installer'е создал 39 каналов-сирот —
  автоматика минта всегда должна упираться в человека.
- **Бэкап** состояния на VPS ежедневно + проверка восстановления.
- Обновления ядра — вручную из team-линии, скилл `deploy-core`.

Ручные операции админа сегодня: обновить куки по 🟠 (скилл
`refresh-cookies`); пополнить пул комнат с мака при всплеске выпусков
(`scripts/refill_cups_pool.py`, необязательно — бот сам минтит).

## Целевой контур: массовый сбой носителя → переезд без админа

Сценарий: носитель X (например, cupsonline) перестал работать у всех.
Требование: **бот сам пишет активным пользователям и выдаёт новые
ссылки уже на запасном носителе; возврат на основной — тоже
автоматически по восстановлению.**

- [x] **R1. Здоровье носителя, а не только канала** (2026-10-27):
      пробник носителя — read-only GET страницы, в которой сидит канал
      (cups room shell / telemost join), вердикт по всем каналам
      носителя сразу; порт-проба осталась только прямым каналам.
- [x] **R2. Помечать носитель** (2026-10-27): `CarrierMonitor`
      (антидребезг K/M как у каналов), файл `carrier-state.json`
      переживает рестарт бота.
- [x] **R3. Переезд на запасной — только руками пользователя** (решение
      админа 2026-10-28, после ночного инцидента с авто-минтом): при
      смерти носителя бот шлёт каждому его пользователю ОДНО
      предупреждение за эпизод («сделай /rotate — получишь свежую
      ссылку на рабочем носителе») и 🚨 админу; сам бот ссылки не
      минтит никогда. `/rotate` и `/issue` на мёртвом носителе
      переезжают на запасной (новый ключ, старый канал отзывается).
- [x] **Кулдаун смены канала** (2026-10-28): `/rotate` и переезд — не
      чаще раза в 10 минут на канал (метка `rotated` в реестре).
- [x] **R4. Возврат на основной** (2026-10-27/28): носитель
      восстановился (M проб) → бот пишет админу 🟢 и предлагает
      переехавшим вернуться («хочешь назад — /issue»); переезд назад —
      только по желанию пользователя.
- [x] **Антидребезг флапа** (2026-10-28): 3-й срыв носителя за час →
      «unstable» — алерты замолкают, возврат требует M×4 хороших проб;
      user-initiated переезды доступны всё время.
- [x] **R5. Тесты флоу**: юнит-тесты вердиктов/предупреждений/флапа/
      кулдауна — сделаны. Живой прогон 2026-10-27 (блок cups на VPS):
      детект, вердикт, переезд и полный откат при недоставке —
      подтверждены живьём; финальная доставка не дожата из-за сбоя
      VPS↔Telegram (не наш путь).

## Сопутствующая автоматика (детали, которые легко забыть)

- [ ] **Алерты на ресурсы выпуска**, чтобы админ узнавал ДО жалоб:
      пул комнат < 1 сета; диск VDS > 90% (инцидент 2026-10-25: диск
      100% сломал rotate); ошибки создания telemost-конференций.
- [ ] **Сессия telemost**: watchdog пробует создание конференции раз в
      сутки; протухла → 🟠 «обнови telemost-сессию» (процедура: логин в
      telemost + захват запроса, описана в `telemostconf.py` и TR-11).
- [x] **Истечение конференции у неактивного пользователя** (2026-10-28):
      telemost-конференция живёт ~24 ч без активности — при живом
      носителе владелец умершего канала получает предупреждение
      «сделай /rotate» (один раз за эпизод).
- [ ] **Пул**: предпополнение с мака по желанию (launchd на
      `refill_cups_pool.py`, держать ≥ 2 сета) — снижает риск упереться
      в 403-лимит cups при массовом выпуске; не обязательно (бот минтит
      сам, лимит ~40 комнат/день с IP).
- [ ] **iOS**: TestFlight-сборка несёт ядро 0.7.3 — не подключается ни
      к одному носителю (апстрим #190). Ждём сборку с ядром ≥ 0.15.x от
      @saharev1; до тех пор iOS-пользователей не выпускать.
- [ ] **Чистка**: раз в неделю бот напоминает админу удалить
      протухшие тестовые конференции/комнаты (список даёт реестр).

## Эксплуатация после R1–R5 (целевая рутина админа)

1. 🟠 «куки протухли» → скилл `refresh-cookies` (5 минут в браузере);
2. 🟠 «сессия telemost истекла» → логин в telemost + захват запроса;
3. 🟢 на всё остальное — ничего не делать.

## Открытые вопросы

- Верхняя граница каналов на VDS (1 GB) до деградации — замерить перед
  ростом; память на канал снять в нагрузочной.
- DNS клиента через tun (UDP NAT в l3) — проверять живым tun-клиентом.
- Dual-транспорт в одной ссылке — вернуть, когда ядро починит
  переключение (наш repro отправлен в TR-10, апстрим #198/#204).
