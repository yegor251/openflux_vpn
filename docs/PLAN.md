# План работ: multi-user VPN на OpenFlux (yandex + mailru)

Цель: готовое решение «личный VPN для многих пользователей» без
бизнес-части. Каждый пользователь — свой канал: ключ + документы-посредники
на Яндекс.Доках и Mail.ru + exit-инстанс на VDS. Управление — CLI на
машине администратора.

```
oflux-admin (наш код, Python)
   │ ключ + docprovider (готов) + SSH node-install.sh + openflux://-ссылка
   ▼
VDS: systemd-каналы openflux-node@<user> (по одному активному клиенту)
   ▲
пользователь: openflux://-ссылка → готовое приложение (Desktop/Android/CLI)
```

Технические подробности библиотеки и модуля документов — не здесь:
`src/docprovider/README.md` (поведение docprovider, live-контракты API,
грабли) и исходники `OpenFlux/`.

## M2 — `oflux-admin add-user` end-to-end

Цель: команда `add-user <name>` доводит от нуля до рабочего VPN
пользователя ≤ 3 минут, без ручных шагов.

- [ ] Проверить, что `node-install.sh` поддерживает микс
      yandex+mailru в одном канале; если нет — минимальный патч
      инсталлятора или свой генератор node.conf (формат `[Transport "..."]`
      ядро умеет).
- [ ] Выбрать режим ноды: l3 (быстрее, root + iptables-правило против
      kernel-RST) или l4 (дефолт инсталлятора, без root). Рекомендация — l3.
- [ ] SSH-обвязка на paramiko: выполнение `node-install.sh`
      (apply/remove/list) с sudo-паролем через stdin; референс —
      `provision.Dial/Plan/Apply/Remove` в ядре.
- [ ] Реестр `users.json` (0600): имя → {channel, key, port, yandex-url,
      mailru-url, vds, created, revoked}. Версионирование формата с первого дня.
- [ ] Конфиг серверов `servers.yaml`: SSH-алиас, лимит каналов,
      диапазон портов; планировщик размещения в add-user.
- [ ] systemd drop-in на канал: MemoryMax/CPUWeight/TasksMax/LimitNOFILE
      (жадный пользователь не должен топить соседей).
- [ ] add-user: ключ (`secrets.token_hex(32)`) → doc-provider → канал на
      VDS → `make_link` + QR в `out/<name>.png`.
- [ ] Критерий: клиент подключается по выданной ссылке; failover
      yandex→mailru проверен вырубанием яндекс-дока.

## M3 — жизненный цикл

- [ ] `list` (таблица пользователей/каналов/портов/серверов).
- [ ] `link <name>` — перевыпустить ссылку и QR.
- [ ] `rotate <name>` — новый ключ в node.conf + рестарт канала + новая
      ссылка (документы не трогаем).
- [ ] `revoke <name>` — remove канала на VDS + unpublish документов +
      пометка в реестре. Мгновенно, без затрагивания соседних каналов.
- [ ] `doctor <name>` — статус systemd, живость обоих документов, тест
      direct-порта.
- [ ] Мульти-VDS: переполнение сервера → подсказка/авто-выбор следующего.

## M4 — эксплуатация

- [ ] Плановое обновление кук обоих сервисов (процедура + напоминание;
      detection — `CookiesExpiredError` / csrf 403, см. docprovider README).
- [ ] Пул аккаунтов-посредников: 3–5 аккаунтов, дневные лимиты
      (≤5 доков/день/аккаунт), ротация при подборе в add-user.
- [ ] `doctor` по расписанию + алерты на мёртвые каналы и протухшие куки.
- [ ] Нагрузочная проверка: 10–20 каналов на VDS (CPU/RAM/трафик),
      снять реальные цифры памяти на канал для планирования ёмкости.
- [ ] Критерий: неделя работы 5+ каналов без ручного вмешательства.
