# Зачем нужна маскировка (direct vs посредники)

Зафиксировано: 2026-10-19. Контекст: каналы сейчас работают в режиме
**direct-only** (шифрованный TCP до VPS, без посредников), и это
рабочее состояние. Документ отвечает на вопрос «зачем тогда
возиться с яндекс-лейном» и фиксирует критерии, когда к этому
вернуться.

## Как direct выглядит снаружи

Клиент держит постоянное шифрованное TCP-соединение с нестандартного
порта на IP дата-центра (наш VPS). Протокол не виден (AES-256-GCM),
но **паттерн виден идеально**: долгоживущий шифрованный туннель на
посторонний сервер — классический профиль персонального VPN.

## Что умеет ТСПУ и когда direct умирает

1. **Чёрные списки IP.** Если IP VPS попадает в блок (дешёвые хостеры
   улетают целыми подсетями), direct умирает мгновенно — и умирают
   **все каналы всех пользователей бота разом**.
2. **Эвристика DPI.** ТСПУ всё чаще режет «неизвестные шифрованные
   туннели» не по сигнатуре, а по поведению (ритм пакетов, время
   жизни соединения). Тогда direct начнёт лимитироваться/резаться без
   всякого списка. Апгрейда в direct-режиме нет: прятать протокол
   уже нечем.
3. Адресация: в direct клиент обращается напрямую к IP VPS — этот IP
   и есть единственная точка отказа.

## Что даёт маскировка (живой яндекс-лейн)

Трафик выглядит как обычная работа с `docs.yandex.ru` — TLS/WebSocket
на инфраструктуру Яндекса:

- блокировать это = блокировать сам Яндекс (для ТСПУ неприемлемо);
- IP VPS **не участвует** в адресации клиента → его блокировка
  бессмысленна;
- нет паттерна «туннель» — есть паттерн «работа с документами».

## Сравнение

| Сценарий | direct | с маскировкой |
|---|---|---|
| Сейчас: чистый IP, лояльный маршрут | работает | работает |
| VPS попал в чёрный список | 💀 все каналы | работает |
| ТСПУ режет неизвестные туннели | 💀 | работает |

**Вывод:** маскировка — страховка от двух сценариев смерти и исходная
цель проекта (обход белых списков ТСПУ). Жизнь на direct — валидный
выбор, пока не сработал один из триггеров ниже.

## Статус на 2026-10-19 и что мы узнали 2026-10-18

- Оба транспорта-посредника отключены внешними событиями:
  `mailru` — закрыт анонимный доступ (апстрим #193), `yandex` —
  SmartCaptcha/login-стены (апстрим #106).
- **Проверен механизм передачи кук через приложение** (экран «узел не
  может пройти проверку»): канал приложение→нода **работает** — 18 кук
  легли в стор ноды. Но в банке оказались только аналитические куки:
  вебвью приложения сам падает после PoW на редакторе («файл не
  найден»), нода ловит ту же ошибку на docviewer (403).
- Остался один диагностический тест: инкогнито-открытие URL дока с
  чистого IP. Редактор откроется → проблема в IP ноды; «файл не
  найден» → Яндекс закрыл анонимный редактор глобально (новое
  закрытие API вдогонку #193).

## Критерии возврата к маскировке (любой из)

1. VPS попал в чёрный список или каналы начали массово отваливаться.
2. Появились признаки эвристического душения direct (медленно/рвётся
   при работающем канале на сервере).
3. Апстрим закрыл #106/#193 или нашёл обход редактора — тогда
   возвращает яндекс-лейн одной веткой (обвязка сохранена:
   docprovider, cookie-store, скилл кук).
4. Пользователь сам хочет маскировку — тогда первым шагом тест
   инкогнито из раздела выше.

Практическая деградация при жизни на direct: без маскировки, но с
шифрованием; при блокировке VPS — миграция на новый хост и
пере-выпуск ссылок (кнопки `/rotate` недостаточно — меняется host/port;
см. `docs/PLAN.md`).
